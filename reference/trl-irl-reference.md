# TRL and IRL Reference

**Authoritative source for TRL:** Department of Defense, *Technology Readiness Assessment Guidebook*, February 2025 (OUSD(R&E), cleared for public release; supersedes the June 2023 Guidebook, the 2009 TRA Deskbook, and the 2011 TRA Guidance). Tables 2-1 (hardware), 2-2 (software), and 2-3 (terms) are reproduced below with the wording of the Guidebook. The GAO *Technology Readiness Assessment Guide* (GAO-20-48G, January 2020) carries the same nine definitions and its Table 4 matches the DoD supporting-information columns.
**Source for IRL:** Sauser, Gove, Forbes, and Ramirez-Marquez, "Integration maturity metrics: development of an Integration Readiness Level" (Stevens Institute; INCOSE 2008), Table 1, citing Gove 2007. IRL is a published systems-engineering scale used by DAU and by platforms such as Vulcan; it is not DoD policy the way TRL is.
**Compiled:** 2026-09-08 for proposal use. Section 4 is EdgeRunner's own rule set for making a TRL claim; everything above it is the Government's language.

## 1. The nine TRLs, hardware and software side by side

| TRL | Definition (hardware, Table 2-1) | Definition (software, Table 2-2) | What the software level means | Evidence a software claim needs (supporting information) |
|---|---|---|---|---|
| 1 | Basic principles observed and reported. | Basic principles observed and reported. | A new software domain is being investigated by the basic research community: basic use, basic properties of software architecture, mathematical formulations, general algorithms. | Basic research activities, research articles, peer-reviewed white papers, point papers, early lab model of basic concept. |
| 2 | Technology concept and/or application formulated. | Technology concept and/or application formulated. | Practical applications invented but speculative; no proof or detailed analysis. Analytic studies using synthetic data. | Applied research activities, analytic studies, small code units, papers comparing competing technologies. |
| 3 | Analytical and experimental critical function and/or characteristic proof of concept. | Analytical and experimental critical function and/or characteristic proof of concept. | Scientific feasibility shown through analytical and laboratory studies. Limited-functionality environments validate critical properties, including cybersecurity, with non-integrated components and partially representative data. | Algorithms run on a surrogate processor in a laboratory; instrumented components operating in a laboratory; laboratory results validating critical properties. |
| 4 | Component and/or breadboard validation in a laboratory environment. | Module and/or subsystem validation in a laboratory environment (software prototype development environment). | Basic software components integrated to show they work together; primitive in efficiency and robustness. Architecture work begins on interoperability, reliability, maintainability, extensibility, scalability, security. Emulation with legacy elements. | Advanced technology development; stand-alone prototype solving a synthetic full-scale problem; stand-alone prototype processing fully representative data sets. |
| 5 | Component and/or breadboard validation in a relevant environment. | Module and/or subsystem validation in a relevant environment. | Ready to start integration with existing systems. Prototype conforms to target environment and interfaces. Experiments with realistic problems; simulated interfaces to existing systems; system software architecture established; algorithms run on processors with the characteristics expected operationally. | System architecture diagram with critical performance requirements; processor selection analysis; Sim/Stim laboratory build-up plan; software under configuration management; COTS/GOTS components identified. |
| 6 | System/subsystem model or prototype demonstration in a relevant environment. | Module and/or subsystem validation in a relevant end-to-end environment. | Engineering feasibility demonstrated. Laboratory prototype on full-scale realistic problems, partially integrated with existing hardware and software. Cybersecurity verification included in testing. | Laboratory test results for a prototype near the desired configuration including physical, logical, data, and security interfaces; the tested-versus-operational environment difference analytically understood; measurements of throughput, scalability, reliability contribution; human-computer analysis begun. |
| 7 | System prototype demonstration in an operational environment. | System prototype demonstration in an operational, high-fidelity environment. | Program feasibility demonstrated. Operational-environment prototype where critical technical-risk functionality is available for demonstration and test, well integrated with operational hardware and software. | Critical technological properties, including cybersecurity, measured against requirements in an operational environment. |
| 8 | Actual system completed and qualified through test and demonstration. | Actual system completed and mission qualified through test and demonstration in an operational environment. | Fully integrated with operational hardware and software. Development documentation complete. All functionality and cybersecurity measures tested in simulated and operational scenarios. | Published documentation and technology-refresh build schedule; software resource reserve measured and tracked; all severity 1 and 2 defects resolved, reasonably low severity 3 backlog. |
| 9 | Actual system proven through successful mission operations. | Actual system proven through successful mission-proven operational capabilities. | Readily repeatable and reusable. Fully integrated; all documentation verified; successful operational experience; sustaining engineering in place. | Production configuration-management reports; defect resolution system and process in place for deployed software. |

The hardware column's descriptions, for completeness: TRL 5 "high-fidelity laboratory integration of components"; TRL 6 "testing a prototype in a high-fidelity laboratory environment or in a simulated operational environment"; TRL 7 "demonstration of an actual system prototype in an operational environment (e.g., in an aircraft, in a vehicle, or in space)"; TRL 8 "developmental test and evaluation of the system in its intended weapon system"; TRL 9 "operational test and evaluation (OT&E)".

## 2. The environment terms (Table 2-3), which decide 5 versus 6 versus 7

| Term | Guidebook definition |
|---|---|
| Relevant environment | Testing environment that simulates both the most important and most stressing aspects of the operational environment. |
| Simulated operational environment | Either (1) a real environment that can simulate all the operational requirements and specifications required of the final system, or (2) a simulated environment that allows for testing of a virtual prototype. Used to determine whether a developmental system meets the operational requirements and specifications of the final system. |
| Operational environment | Environment that addresses user operational requirements and specifications required of the final system, to include platform and packaging. |
| High fidelity | Addresses form, fit, and function. A high-fidelity laboratory environment can simulate and validate all system specifications within a laboratory setting. |
| Low fidelity | Limited to first-order information about the end product; used for trend analysis. |
| Breadboard | Integrated components that represent a system or subsystem for concept feasibility; laboratory-configured; may resemble the final system in function only. |
| Model | A functional form of a system, generally reduced in scale, near or at operational specification, hardened enough to demonstrate the required technical and operational capabilities. |
| Prototype | A physical or virtual model used to evaluate the technical or manufacturing feasibility or military utility of a technology, process, concept, end item, or system. |

**The Guidebook's test for "relevant environment" (section 2, page 12).** A relevant environment is a set of stressing conditions, representative of the full spectrum of intended operational employments, applied to the technology as part of a component (TRL 5) or system/subsystem (TRL 6). One or a few demonstrations under favorable conditions do not meet it. Demonstration requires trial testing that either validates the required functionality across the full spectrum of intended employments, or validates it for the important intended employments and then uses accepted analytical techniques to extend confidence across the rest.

**Worked reading of the three levels that matter to us.**

| Level | The question an assessor asks | Passes | Does not pass |
|---|---|---|---|
| 6 | Did a near-final prototype run end to end on a full-scale realistic problem, in conditions that simulate the stressing parts of the mission, partially integrated with the real systems around it? | A lab or field exercise with representative data, representative hardware class, and the real interfaces stubbed or partially live. | A demo on a curated dataset in a conference room; a component running alone; favourable conditions only. |
| 7 | Did the system prototype run in the operational environment, integrated with the operational hardware and software, with the risky functions exercised and measured against requirements? | A unit's own data on the unit's own systems in a field event or deployment, with an assessment record. | A relevant environment however good; a demo where the risky function (for example the simulation or BDA piece) was not exercised. |
| 8 | Is the actual system complete and qualified in that environment, documented, with severity 1 and 2 defects closed? | Program-of-record fielding with acceptance testing. | A prototype, however well it ran. |

## 3. Integration Readiness Level (IRL)

| IRL | Definition (Gove 2007; Sauser et al. 2008) | Description | Stage |
|---|---|---|---|
| 9 | Integration is mission proven through successful mission operations. | The integrated technologies are used successfully in the system environment. Reaching IRL 9 also implies maturing the component technology to TRL 9. | Pragmatic |
| 8 | Actual integration completed and mission qualified through test and demonstration in the system environment. | The integration meets requirements and there is a system-level demonstration in the relevant environment, which reveals defects that only appear when the integrating technologies interact in the system environment. | Pragmatic |
| 7 | The integration of technologies has been verified and validated with sufficient detail to be actionable. | A significant step beyond IRL 6: the integration works technically and meets requirements such as performance, throughput, and reliability. | Syntactic |
| 6 | The integrating technologies can accept, translate, and structure information for the intended application. | The highest technical level: control of the integration, plus specifying what information to exchange, unit labels for what the information is, and translation from a foreign data structure to a local one. | Syntactic |
| 5 | There is sufficient control between technologies to establish, manage, and terminate the integration. | One or more of the integrating technologies can control the integration itself: establish, maintain, terminate. | Syntactic |
| 4 | There is sufficient detail in the quality and assurance of the integration. | Beyond simple data exchange: the data sent is the data received, and a mechanism exists to check it. Many integration failures never progress past IRL 3 because exchange is mistaken for integration. | Syntactic |
| 3 | There is compatibility (a common language) between technologies to orderly and efficiently integrate and interact. | The minimum level for successful integration: the technologies influence each other and communicate interpretable data. | Semantic |
| 2 | There is some specificity to characterize the interaction (ability to influence) between technologies through their interface. | A signalling method is selected so the two technologies can influence each other over the chosen medium; integration proof of concept. | Semantic |
| 1 | An interface between technologies has been identified with sufficient detail to allow characterization of the relationship. | The lowest level: a medium for integration has been selected. | Semantic |

IRL is scored per integration point, not per system. An offer with three integrations (say, a COP, a simulation engine, and a data feed) has three IRLs, and the lowest one is the honest headline. IRL 7 requires a requirements-level verification of the integration, not a working demo.

## 4. EdgeRunner rules for stating a TRL (house doctrine, not Government text)

1. **The claim names four things or it is not a claim:** which component or which integrated configuration, in what environment (by the Table 2-3 term), assessed by whom, and when. "TRL 7" alone is a Weakness waiting to be written.
2. **Integrated solution and component are different claims.** A solicitation that scores the whole solution (the NAVWAR EPSS Q&A 28 pattern) gets the TRL of the least mature required component. A component that has never been exercised against the mission function it is offered for is not at 7 because the platform it sits on is.
3. **Bill's rule (Slack, 2 September 2026):** TRL 7 is defensible for anything demonstrated at EXTiC 26-2, deployed with a unit, or run under a CRADA or pilot; in general, anything demonstrated with real-world data or systems in a test environment. That matches the Guidebook's TRL 7 "operational environment, well integrated with operational hardware and software" only when the risky function was actually exercised there. If it was not (John's WarRoom case: simulation and BDA were not demonstrated), 6 is the number, and the brief should say which components are at 7 and cite the event.
4. **Cite the ledger.** Every TRL statement carries an evidence marker to the record of the assessment: EXTiC 26-2 is EV-131 (thirteen of thirteen objectives, independent assessor, tactical laptop hardware, no external network); First Army verification is EV-130 and EV-073; the Space Force IL-5 ATO is EV-022. A TRL without a ledger item is `CLAIM-UNSUPPORTED`.
5. **Do not let an assessor's TRL become ours by osmosis.** EV-131 records that EdgeRunner self-reported TRL 8 and the assessor recorded what was demonstrated. Quote the assessor's finding; state our own TRL in our own voice with its basis.
6. **Software TRLs need software evidence.** For 6 and above the Guidebook expects cybersecurity verification in the test, interface-level results, and measured throughput, scalability, and reliability. Have the numbers or do not claim the level.
7. **Never generalize a TRL across environments.** IL-6 IATT, IL-5 ATO, and a field event are separate facts about separate configurations. State each where it applies.

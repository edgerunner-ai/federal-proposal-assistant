# Federal Proposal Assistant — Review & Recommendations

**Date:** 2026-04-20
**Context:** Reviewed after shipping 7+ phases on capture-pipeline
(ending with the Go/No-Go Assessment framework, CSO vehicle tracking,
and in-app changelog). This document captures what's working well in
the proposal assistant, what could be improved by applying lessons
learned from the capture side, and what to skip.

**TL;DR:** The proposal assistant is architecturally sound. The
changes that would genuinely move the needle are small, focused, and
mostly orthogonal to each other — not a big-bang restructuring. Most
of Grok's consultant-style recommendations about merger, LangGraph,
RAG, and Streamlit should be declined on cost/benefit grounds.

---

## What's Working Well (Preserve)

1. **Prompt-first, CLI-driven skill architecture.** Twelve focused
   skills each with a clear scope and written contract. Claude Code
   skills compose naturally with Read/Write/Bash. This beats any
   orchestration framework I've seen proposed — the human stays in
   the driver's seat at every stage gate.
2. **Folder-based artifact storage.** `inputs/` → `working/` → `drafts/`
   → `reviews/` → `final/` is a clean progression. Git tracks history;
   filesystem is the database. No servers, no synchronization concerns,
   CUI-compliant by default.
3. **`my-company/` as central knowledge.** One profile, read by every
   skill. No invented past performance. Single source of truth the
   company itself maintains.
4. **`CLAUDE.md` operating discipline.** The priorities, rules, and
   standard workflow embedded at the top are the model's durable
   context. Clear and enforceable.
5. **Capture modes (Full Capture vs. Responsive).** A single field in
   `working/proposal-brief.md` changes behavior across every skill.
   Minimal ceremony, high leverage.
6. **Evaluator mindset.** Skills consistently say "write for a GS-14
   evaluator with a scoring rubric." Reviews anchor to
   findability-within-30-seconds. This framing keeps the output
   grounded.

**None of these should be restructured.** They are the load-bearing
elements of the tool.

## Lessons from Capture-Pipeline Worth Porting

The capture-pipeline side has spent the last month accumulating
patterns that would translate cleanly to the proposal workspace
without changing its prompt-first architecture.

### 1. Source provenance tags on every AI-generated field

**What we do in capture:** Every editable field on an opportunity
carries a `source` tag — `user` or `ai_quickvet`. AI-inferred values
render with a ✨ badge and "click to confirm" tooltip; any human edit
flips the source to `user` and the badge disappears.

**Why it matters:** Lets the user trust the workspace. Fields that
are "official" (human-confirmed) look different from "AI-suggested"
(still needs review). No ambiguity, no lost provenance.

**How to port:**
- When a skill writes a draft section, prepend a small frontmatter
  block with `ai_generated: true`, the model, and a timestamp.
- A `/confirm-section` or equivalent skill (or just a convention:
  delete the frontmatter on first human edit) flips the file to
  "human-approved."
- The red-team skill can treat `ai_generated: true` files as
  higher-suspicion targets.

**Effort:** 1-2 hours per skill, mostly adding frontmatter to `Write`
calls. Red-team skill gets an extra rule.

### 2. Structured verdicts with evidence lists alongside narrative

**What we do in capture:** The Go/No-Go Assessment doesn't just say
"this opportunity is a good fit." It emits four verdicts
(feasible/marginal/not_feasible, strong/moderate/weak) each with a
rationale AND a list of specific evidence points (matched
capabilities, gating factors, gaps, differentiators). The UI renders
color-coded chips so the verdict is parseable in 2 seconds; the
rationale and evidence are available for the human who wants depth.

**Why it matters:** LLM output is more useful when it commits to a
structured conclusion *and* shows its work, rather than generating
prose that the human has to parse for the answer.

**How to port:**
- **`capture-scorecard` skill** already has this shape (9 dimensions
  with R/Y/G). Make sure its output also emits machine-readable
  JSON alongside the markdown, so downstream skills can key decisions
  off it (e.g., a red `pricing_risk` score gates the `pricing-analyst`
  skill into asking more questions).
- **`red-team-review` skill** should emit findings as a structured
  list: `[{severity: high|medium|low, section: ..., issue: ...,
  evidence: [...], suggested_fix: ...}]`. The writer/manager can
  then address each finding traceably.
- **`competitor-assessment` skill** similarly — each competitor gets
  a structured profile with explicit `teaming_viability` and
  `threat_level` verdicts, not just prose.

**Effort:** Medium (~half a day per skill). Pure additive — append a
structured block to the existing markdown output. Downstream consumers
can ignore it until they're ready to use it.

### 3. Activity timeline / audit trail

**What we do in capture:** Every state change on an opportunity
(stage advance, field edit, LLM scoring, disposition) writes an entry
to an `activity_log` table with actor, timestamp, action_type,
old/new values, and metadata. The detail page renders a chronological
view so a user returning to an opportunity after a week can see what
happened.

**Why it matters:** Federal proposals are multi-week efforts with
multiple people and pauses. When you come back to a proposal on day 18,
remembering what you'd decided and why is expensive. A durable trail
avoids the "did we already decide to team with BigBear.ai?" problem.

**How to port:**
- **Lightweight**: each skill appends a single line to
  `working/activity.md` on completion:
  `## 2026-04-20 14:30 — red-team-review (gold) — 4 high, 7 medium findings in reviews/gold-team.md`
- **Heavier**: skills append structured JSONL entries to
  `working/activity.jsonl` that a future dashboard can parse.
- The new-proposal skill seeds an empty `activity.md` and the
  proposal-brief links to it.

**Effort:** Small. One shared helper convention (e.g., "every skill
appends one line on success") across twelve skills.

### 4. Test coverage for the outputs, not just the code

**What we do in capture:** 274 tests. A lot of them are "render the
opportunity detail page with this fixture, assert the right classes
and text appear." Catches template drift, schema breaks, and
accidental regressions.

**Why it matters:** The proposal assistant today has no automated
tests — skill quality is eyeballed. That's fine for an expert user
(Bill) operating it by hand, but it means any change to a skill's
prompt has no guardrail.

**How to port:**
- **Golden-file tests for skills.** For each skill, maintain 1-2
  "canonical input" scenarios in `tests/fixtures/` and a "canonical
  output" file. A simple pytest runs the skill and diffs the output
  against the golden file. Output shape drift (missing a section,
  dropping a field) fails the test.
- **Schema validation.** JSON structured outputs (per #2 above) get a
  schema and a test that says "parse it, validate against schema,
  must pass."
- **Smoke test: a full pass through a small sample proposal.** End
  to end, `/new-proposal` → `/proposal-manager` → ... → `/red-team`,
  asserting each stage writes its expected file.

**Effort:** Medium. Initial setup is a day; maintenance is cheap
because prompt changes don't usually break structure.

**Note:** This only works if Claude Code is scriptable enough to run
skills in a test harness. If not, lighter-weight: JSON schema
validation on the structured portions of each skill's output.

### 5. Cost transparency on billable AI actions

**What we do in capture:** The Quick Vet button says `~$0.01`. The
Suggest Next Steps button says `~$0.02`. Users know what they're
spending before they click.

**Why it matters:** Federal proposal work runs through Claude Code
which can rack up meaningful token costs on long proposals (especially
with graphics + red team + writer on a 50-page RFP). An operator
running the tool for a small biz should have a rough sense of what
each skill costs.

**How to port:**
- Each SKILL.md declares an approximate token cost and rough dollar
  estimate at the top (e.g.,
  `Approx cost: 3-5 min runtime, ~$0.10-0.30 per invocation`).
- Skills that make many LLM calls internally (proposal-writer on a
  long section) can note that explicitly.

**Effort:** Trivial. Documentation only; update during skill revisions.

### 6. Multi-tenant / per-company isolation discipline

**What we do in capture:** Multi-tenant deployment taught us that
shared YAML defaults silently leak across tenants. The fix was to
treat DB-backed per-company configs as authoritative once they exist,
with YAML only as a last-resort fallback for truly fresh installs.

**Why it matters:** The proposal assistant is single-tenant today
(one `my-company/`), but the architecture invites future multi-user
scenarios (a BD consultant running it for three clients). The
isolation patterns we learned apply directly.

**How to port:**
- **Defense in depth on `my-company/` reads.** Every skill should
  confirm `my-company/company-description.md` exists before reading.
  If missing, fail loudly, don't silently fall back to a placeholder.
- **If/when multi-proposal shared state emerges** (e.g., a
  cross-proposal partner database), treat each proposal's `inputs/`
  as the authoritative scope for that proposal. Don't let one
  proposal's teaming-partner list leak into another's draft.

**Effort:** Small. Mostly a "no generic fallbacks" policy documented
in CLAUDE.md.

### 7. Schema-versioned contracts between skills

**What we do in capture:** The export payload carries
`schema_version: "1.0"`. The import skill validates the version.
When we bump the schema, consumers know to re-check their handling.

**Why it matters:** Skills that read each other's outputs are
brittle without a contract. If `proposal-manager` writes
`working/proposal-plan.md` in a format that the `proposal-writer`
skill depends on, any change to one is a potential break of the other.

**How to port:**
- Each skill that writes structured output includes a
  `plan_version` or similar frontmatter field.
- Skills that read upstream files check the version; if the version
  is newer than they know, warn the user and degrade gracefully
  instead of silently reading wrong fields.

**Effort:** Small. Frontmatter convention + a one-line check in
consumer skills.

## What I'd Skip

All these were suggested in Grok's review. They're consultant-grade
proposals that add infrastructure for problems the tool doesn't have.

### Skip: Full merger into a monorepo

The capture-pipeline and proposal-assistant solve opposite
architectural problems (always-on web app vs. per-proposal CLI
workspace). Merging them forces each to carry complexity it doesn't
need. The JSON handoff (shipped today) is the correct integration
point.

### Skip: LangGraph state machine

A federal proposal is not an agent task. It's a multi-week human-led
effort with deep expert review at every stage. Claude Code skills
already give you on-demand tool invocation; a state machine would
black-box work that needs human-driven gating.

### Skip: RAG over `my-company/` and past proposals

Your `my-company/` is ~50KB. It fits in a 200K context window four
times over. You have ~5 past proposals — not 500. RAG solves "I
can't fit the knowledge in a prompt"; you don't have that problem.
Revisit when you have 100+ past proposals and actual retrieval quality
problems.

### Skip: Streamlit / React dashboard

This would compete with Claude Code CLI as the primary interface.
Claude Code is working well. A dashboard adds a UI layer you have to
maintain, with no quality lift on the output (the work is the
prose + graphics, not the dashboard).

### Skip: "Master orchestrator `/run-proposal` with parallel skills"

Proposal phases have hard dependencies. You don't want "architecture"
and "writer" running in parallel against different assumptions. The
existing manual invocation flow preserves the human stage gates that
make good proposals possible.

### Skip: Self-critique loops on every LLM call

Useful for short structured outputs (scorecards, red-team findings).
Actively counterproductive for long-form narrative where the expert
reviewer is the human. Adds latency and cost without meaningful
quality lift.

### Skip: "Convert all skills to structured JSON-mode"

Proposals are narrative + graphics. JSON-mode is the right tool for
the scorecard / red-team / compliance-matrix outputs (see
recommendation #2 above), but wrong for prose sections. Apply it
surgically, not uniformly.

## Prioritized Recommendations

If time were scarce, here's the order I'd tackle the porting:

### P1 (do first — high value, low effort)

1. **Activity trail** (recommendation #3). One-line append per skill
   execution to `working/activity.md`. A half-day of skill updates
   yields a durable audit view that matters on long proposals.
2. **Structured verdicts alongside narrative** for capture-scorecard,
   competitor-assessment, and red-team-review (recommendation #2).
   These three skills benefit most because their outputs gate
   decisions.
3. **Cost transparency** (recommendation #5). Documentation pass
   across all twelve SKILL.md files. One afternoon.

### P2 (do when you feel the pain)

4. **Source provenance on drafts** (recommendation #1). Worthwhile
   when you start revising drafts and lose track of what was
   AI-generated vs. human-edited. Until then, memory suffices.
5. **Schema-versioned inter-skill contracts** (recommendation #7).
   The day a skill breaks because another skill changed its output
   shape, do this.

### P3 (larger investments, don't rush)

6. **Automated skill tests** (recommendation #4). Worth it once the
   skill set is stable and you're no longer iterating on prompts.
   Premature test coverage on evolving skills is expensive
   maintenance.
7. **Multi-tenant isolation discipline** (recommendation #6). Only
   if you ever stand up a shared workspace. As a single-tenant
   tool, today's design is fine.

## The Handoff

The `import-from-capture` skill (shipped today at
`.claude/skills/import-from-capture/`) eliminates the retype tax
between capture and proposal. That's the single highest-value
integration between the two tools — you don't need any more.

If you want to extend it later:

- **Reverse handoff.** When a proposal ships (lands in `final/`),
  the proposal assistant could POST a status update back to the
  capture-pipeline so the opp advances to the Submitted stage
  automatically. Small endpoint on the capture side, small skill
  on the proposal side.
- **Win/loss capture.** When the contract is awarded or not, update
  the opp in capture-pipeline with the outcome + brief rationale.
  Feeds the win-rate analytics you'll eventually want.

Both are incremental additions on top of today's handoff — not a
replatforming.

---

## Closing Note

The prompt-first, skill-based, folder-backed architecture of
the proposal assistant is a strong design that respects the nature of
federal proposal work: high-stakes, expert-driven, human-gated,
artifact-anchored. Don't let anyone talk you into replatforming it.

The refinements above sharpen what's already there. The merger /
monorepo / LangGraph / RAG / Streamlit suggestions would replace a
working tool with a different one that has more moving parts, more
failure modes, and no provably better output. Decline them.
